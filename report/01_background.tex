\section{Verified Compilation Background}

\subsection{Small-Step Operational Semantics}

Giving a formal semantics to a programming language
provides rigorous mathematical meaning to its programs.
Semantic formalisms differ in the level of abstraction
at which they describe computation.
Denotational semantics associate syntactic constructs directly
with abstract mathematical objects.
This approach models programs as functions mapping inputs to outputs,
focusing on the computed result
rather than the intermediate evaluation mechanics.
By contrast,
operational semantics detail the execution process itself,
specifying how a program steps through intermediate configurations
to reach a result.

Operational semantics themselves come in two primary styles.
Big-step operational semantics
evaluate syntactic constructs directly to their final values in a single step.
Complex expressions and compound statements are evaluated compositionally
by combining the evaluation results of their constituent subexpressions.
While big-step semantics offer a concise description of terminating computations,
they struggle to represent non-terminating executions,
concurrency,
or fine-grained non-deterministic choices.

Small-step operational semantics overcome these limitations
by modeling computation as a sequence of elementary transitions.
Rather than evaluating entire expressions or compound statements in a single step,
a small-step semantics describes how the internal state of a program evolves
under individual primitive operations.
This incremental style captures non-termination naturally
as infinite transition sequences
and allows intermediate execution states to be inspected.

Formally,
a small-step operational semantics is defined as a transition system
$(S, \twoheadrightarrow)$,
where $S$ represents the set of program states
and ${\twoheadrightarrow} \subseteq S \times S$ denotes the binary reduction relation.
In our framework,
a state consists of a pair $(s, m)$,
where $s$ is an internal program state and $m$ is a memory.
To allow step transitions to inspect program code
and function declarations,
the reduction relation is explicitly parameterized by the global program $P$.
We write $\step{P}{(s, m)}{(s', m')}$ to indicate that,
under program $P$,
the configuration $(s, m)$ reduces in one step to $(s', m')$.
We denote the reflexive transitive closure of this reduction relation by
$\twoheadrightarrow^{\ast}$.
We do not assume that this step relation is deterministic.

To characterize execution endpoints,
our framework incorporates a partial function \textsf{is\_value},
which maps internal states to optional final return values.
A state $(s, m)$ is considered final
when $\textsf{is\_value}(s)$ yields a value $v$.
For such final states,
we require that no further reduction steps are possible
under any memory configuration in program $P$,
signifying the formal end of execution.

The predicate $\canp{P}{s, m}$ indicates that the state $(s, m)$
can perform a transition in program $P$,
meaning that there exist $s'$ and  $m'$ such that $\step{P}{(s, m)}{(s', m')}$.
Conversely,
a configuration $(s, m)$ is defined as a \emph{stuck state}
in a program $P$ if it is not a final value state
and cannot perform any step in $P$.
Stuck states represent execution failures where semantics are undefined.
For instance,
in an imperative low-level language,
a state becomes stuck when attempting to dereference
an unallocated pointer address,
perform an invalid arithmetic operation such as integer division by zero,
or branch to an invalid control-flow node identifier.

\subsection{Program Behaviors}

Equipped with a small-step operational semantics,
we can formally classify the observable behaviors of a program state.
Because our framework handles non-deterministic languages,
a single initial state may give rise to multiple execution paths,
and thus exhibit multiple behaviors.
For a fixed program $P$,
we classify execution paths into three distinct behaviors:
\begin{itemize}
  \item A state \emph{terminates} with value $v$ and final memory $m$
        if execution reaches a final state $(s', m)$
        such that $\isval{s'} = \Some{v}$.

  \item A state \emph{diverges} if there exists an infinite reduction sequence
        starting from it.
        Note that we do not restrict divergence to strongly diverging states,
        where every execution path is infinite.

  \item A state exhibits \emph{undefined behavior}
        if execution reaches a stuck state.
\end{itemize}

In the following,
we write $b \in s$ to denote that behavior $b$ is exhibited by state $s$.
We extend this notion to a complete program $P$
by considering the behaviors of its initial state.
Having established these behavior categories,
we prove that every state admits an outcome:

\begin{lemma}
For any program $P$,
every state $s$ admits at least one behavior.
\end{lemma}

\begin{proof}
The proof relies on classical logic
by performing a case analysis
on whether state $s$ can reach an ending configuration.
If such an ending state exists,
we prove by induction on the multi-step reduction from $s$
that $s$ exhibits either a terminating or an undefined behavior.
Otherwise,
no reachable configuration can end,
and we establish that $s$ diverges.
\end{proof}

\subsection{Program Refinement}

The objective of a verified compiler is to guarantee
that the correctness properties of a source program
remain valid for the compiled target executable.
When a developer verifies a program using deductive verification
or interactive theorem proving,
the resulting correctness proofs apply to the source code.
To ensure that compilation does not introduce bugs
or invalidate source-level guarantees,
the compiler must preserve semantic behavior.
The presentation below follows the framework of semantic preservation
as introduced by \textcite{leroy-09-compcert}.

A program specification describes the acceptable observable outcomes
of an execution.
Formally,
a specification $\Spec$ is a predicate over behaviors,
written $\Spec(b)$.
A meaningful specification must rule out any undefined behavior:
$\forall b, \Spec(b) \implies b \neq \Undef$.
We say that a program $S$ satisfies a specification $\Spec$,
written $S \vDash \Spec$,
if every behavior exhibited by $S$ satisfies the predicate:
$\forall b, b \in S \implies \Spec(b)$.

Given a source program $S$ and its compiled target executable $T$,
the goal of compiler verification is to guarantee
the \emph{specification preservation} property:
\begin{equation}
  \label{eq:spec-preservation}
  S \vDash \Spec \implies T \vDash \Spec
\end{equation}
Proving specification preservation directly
for each individual specification is impractical,
as the compiler verification proof should remain independent
of specific application requirements.
To decouple compiler verification from specific application requirements,
semantic preservation is established
by proving a \emph{behavioral refinement}
between the target program $T$ and source program $S$:
\begin{equation}
  \label{eq:beh-ref}
  T \sqsubseteq S \coloneqq \forall b, b \in T \implies b \in S
\end{equation}
If this property holds,
then specification preservation~\eqref{eq:spec-preservation}
follows immediately.
This property allows the compiler
to eliminate behaviors of the source program.
For instance,
it enables the compiler to resolve non-deterministic constructs
by selecting a single outcome.

However,
direct behavior refinement~\eqref{eq:beh-ref}
is overly restrictive for optimizing compilers.
If a source program only exhibits undefined behavior,
an optimizing compiler may eliminate an erroneous code path
or transform it into a benign execution for the target.
Because meaningful specifications already exclude undefined behaviors,
to guarantee the \emph{specification preservation}
property~\eqref{eq:spec-preservation},
it suffices to establish a \emph{skewed} behavioral inclusion.

We first define a preorder relation on behaviors:
\begin{gather*}
  \begin{prooftree}
    \hypo{}
    \infer1[Beh-Term]{
      \Term{v}{m} \leqslant_{\text{beh}} \Term{v}{m}
    }
  \end{prooftree}\\[1em]
  \begin{prooftree}
    \hypo{}
    \infer1[Beh-Div]{
      \Div \leqslant_{\text{beh}} \Div
    }
  \end{prooftree}
  \qquad\qquad
  \begin{prooftree}
    \hypo{}
    \infer1[Beh-Undef]{
      b_t \leqslant_{\text{beh}} \Undef
    }
  \end{prooftree}
\end{gather*}

Under this preorder,
a terminating behavior in the source can only be related to the same
terminating behavior in the target.
A diverging behavior in the source can only be related to a diverging behavior
in the target.
However,
an undefined behavior in the source can be refined by any target behavior $b_t$.

With this preorder on behaviors,
we define our notion of \emph{skewed behavior refinement}.
We say that a target state $t$ refines a source state $s$,
written $t \slantsqsubseteq s$,
when:
\begin{equation*}
  t \slantsqsubseteq s
  \coloneqq
  \forall b_t, b_t \in t \implies
  \exists b_s,
  b_s \in s \land b_t \leqslant_{\text{beh}} b_s
\end{equation*}
This relation is lifted to programs ($T \slantsqsubseteq S$)
by relating their initial states.
When a program \emph{refine} another one,
and because we assume specifications rules out undefined behaviors,
we obtain the \emph{specification preservation} property~\eqref{eq:spec-preservation}.

\subsection{Simulation Relations}

While the refinement relation $t \sqsubseteq s$
is formulated globally
in terms of whole-program behaviors,
proving it directly over entire execution traces is impractical.
Compilers perform local transformations
whose correctness is best established step by step.
To bridge this gap,
verified compilation relies on \emph{simulation relations},
which establish an invariant relating the intermediate operational states
of the source and target programs.
This can be done in two flavors:

\begin{description}
  \item[Backward simulation:]
        each execution step taken by the target program must be matched
        by some steps in the source program.
        Because it analyzes every behavior generated by the target
        and maps it back to a valid source execution,
        a backward simulation directly establishes the refinement property
        $t \sqsubseteq s$.
  \item[Forward simulation:]
        each execution step of the source program is matched by corresponding
        steps in the target program.
        Forward simulations are typically much more convenient to construct
        in practice,
        as compiler passes transform source constructs into target code,
        making inductive invariant proofs follow the structure of source
        reductions directly.
\end{description}

A priori,
a forward simulation proves that the target exhibits all behaviors of
the source,
which is the converse of refinement.
However,
when the target language is deterministic,
every target step is uniquely determined.
Under this hypothesis,
a forward simulation implies a backward simulation,
and therefore suffices to establish program refinement.
This is the path used by CompCert to verify
the soundness of its compilation passes.

\subsection{Coinductive Predicates}

Proving a simulation relation requires relating the operational execution
steps of the source and target programs.
When programs terminate,
their execution consists of a finite sequence of reductions ending in a
final state.
Such finite behaviors are naturally formalized using
\emph{inductive} predicates.
However,
many programs are designed to run indefinitely.
For non-terminating executions,
the reduction sequence is infinite and never reaches a terminal base case.
Establishing the simulation inductively is impossible,
as it would require an infinite derivation tree,
which inductive definitions strictly forbid.
To reason about infinite execution traces and divergence rigorously,
we rely on \emph{coinductive} predicates.

The presentation adopted below,
which defines coinduction in terms of infinite derivation trees,
is a simplification adapted to our specific setting.
For an proper definition of coinduction and coinductive predicates,
we refer the reader to
\textcites{milner-89-communication}{gimenez-98-tutorial}{pous-16-cawu}.
Throughout this report,
we define inductive and coinductive relations through sets of inference
rules:
\begin{itemize}
  \item \emph{Inductive rules} are denoted with a single horizontal bar:
        \begin{equation*}
          \begin{prooftree}
            \hypo{H_1}
            \hypo{\dots}
            \hypo{H_n}
            \infer3{\mathcal{I}}
          \end{prooftree}
        \end{equation*}
        Here,
        $H_i$ are the premises and $\mathcal{I}$ is the inductive conclusion.
        A judgment holds inductively if and only if it can be established
        through a \emph{finite derivation tree},
        starting from base cases.

  \item \emph{Coinductive rules} are denoted with a double horizontal bar:
        \begin{equation*}
          \begin{prooftree}
            \hypo{H_1}
            \hypo{\dots}
            \hypo{H_n}
            \infer[coind]3{\mathcal{C}}
          \end{prooftree}
        \end{equation*}
        Here,
        $H_i$ are the premises and $\mathcal{C}$ is the coinductive conclusion.
        They are a generalization of \emph{inductives} rules
        where a judgment holds if it admits a
        \emph{potentially infinite derivation tree}.
\end{itemize}

For instance,
defining finite lists of natural numbers uses induction,
requiring every list to terminate at $\mathsf{nil}$.
In contrast,
infinite streams are defined by coinduction,
allowing endless constructor applications without base cases:
\begin{equation*}
  \begin{prooftree}
    \hypo{}
    \infer1{\mathsf{nil} \in \List{\mathbb{N}}}
  \end{prooftree}
  \qquad
  \begin{prooftree}
    \hypo{n \in \mathbb{N}}
    \hypo{l \in \List{\mathbb{N}}}
    \infer2{\mathsf{cons}(n, l) \in \List{\mathbb{N}}}
  \end{prooftree}
  \qquad\qquad
  \begin{prooftree}
    \hypo{n \in \mathbb{N}}
    \hypo{s \in \Stream{\mathbb{N}}}
    \infer[coind]2{\mathsf{scons}(n, s) \in \Stream{\mathbb{N}}}
  \end{prooftree}
\end{equation*}

These differences in derivation tree restrictions
translate directly into distinct proof principles:
\begin{itemize}
  \item When proving a property over an inductive structure,
        one reasons by induction.
        We proceed by case analysis on the constructors of the inductive
        term ($\mathsf{nil}$ and $\mathsf{cons}$ for lists).
        The induction hypothesis may only be invoked on
        \emph{strictly smaller subterms}.
        This finite descent ensures that the proof eventually terminates at
        a base case.

  \item Conversely,
        when proving that a property holds coinductively,
        one constructs an infinite derivation tree by coinduction.
        The coinductive hypothesis refers to the entire conclusion,
        but it can only be invoked \emph{underneath a constructor}
        ($\mathsf{scons}$ for streams).
        This condition,
        known as \emph{productivity},
        prevents using the coinductive hypothesis to build circular proof
        trees.
\end{itemize}

A detailed example illustrating coinductive reasoning is provided in
\cref{app:stream-bisimilarity}.

The Rocq theorem prover~\parencite{rocq}
supports coinductive predicates natively.
In our formalization,
we use the \texttt{coinduction} library
developed by \textcite{rocq-coinduction}
to facilitate the reasoning
by coinductive simulation invariants.

\subsection{Simulations Schemes \& Stuttering}

Equipped with coinductive predicates to handle potentially infinite
executions,
we can define a simulation relation to establish program refinements.
Given a target program $P_t$
and a source program $P_s$,
a backward simulation relates a target state $t$
to a source state $s$,
ensuring that every execution step taken by the target program
can be matched by the source program.

For terminating executions,
the simulation requires that final states yield identical observable values.
Formally,
if both states reach terminal configurations,
they are related by the following base case:
\begin{equation}
  \label{eq:lock-both-final}
  \begin{prooftree}
    \hypo{\isval{t} = \Some{v}}
    \hypo{\isval{s} = \Some{v}}
    \infer2{t \sim_{l} s}
  \end{prooftree}
\end{equation}

For non-final configurations,
the relation must ensure that the target state is capable of progressing
and that every transition it performs corresponds to an execution step
in the source program.
Because executions may be non-terminating,
this condition is expressed coinductively:
\begin{equation}
  \label{eq:lock-both-step}
  \begin{prooftree}
    \hypo{\canp{P_t}{t}}
    \hypo{\forall t',
      \step{P_t}{t}{t'} \implies
      \exists s',
      \step{P_s}{s}{s'} \land t' \sim_{l} s'
    }
    \infer[coind]2{t \sim_{l} s}
  \end{prooftree}
\end{equation}

The relation $\sim_l$
defined by \cref{eq:lock-both-final,eq:lock-both-step}
is a \emph{lock-step} backward simulation:
the target and source programs advance at the exact same pace.
Under non-determinism,
the target and source states are treated asymmetrically:
\begin{itemize}
  \item The target program exhibits \emph{demonic} non-determinism,
        requiring the simulation to hold for all reachable successor states
        $t'$.
  \item The source program exhibits \emph{angelic} non-determinism,
        meaning that the proof only needs to exhibit the existence of a
        suitable matching successor state $s'$.
\end{itemize}
This asymmetry is precisely what establishes the behavior inclusion.
We must account for all non-deterministic choices of the target
and match each of them with an admissible path in the source.

While lock-step simulations suffice for simple transformations that preserve
step counts,
realistic compiler passes break this correspondence.
An optimization pass such as
branch tunneling removes redundant jump operations,
causing the source program to perform steps that have no counterpart in the
target.
Conversely,
lowering transformations decompose a single high-level source instruction
into multiple low-level target instructions,
requiring the target to execute several steps before the source
advances.

To accommodate passes that alter step counts,
one must allow \emph{asynchronous} execution steps,
where one program takes a step while the other remains stationary.
Such a transition is called a \emph{stuttering} step.
A first coinductive formulation might introduce the following
stuttering rules:
\begin{equation*}
  \begin{prooftree}
    \hypo{\canp{P_t}{t}}
    \hypo{\forall t',
      \step{P_t}{t}{t'} \implies t' \sim s
    }
    \infer[coind]2{t \sim s}
  \end{prooftree}
  \qquad\qquad
  \begin{prooftree}
    \hypo{\step{P_s}{s}{s'}}
    \hypo{t \sim s'}
    \infer[coind]2{t \sim s}
  \end{prooftree}
\end{equation*}

However,
adding these rules to the lock-step simulation $\sim_{l}$
invalidates the refinement between the target and the source.
Without restriction,
a target program could perform infinitely many stuttering steps without the
source program ever progressing.
Under such a definition,
a trivially diverging target program could be related to any source state.

To regain the fact that the target refine the source,
one must guarantee that stuttering remains finite.
This is achieved by equipping the simulation with a well-founded measure
$(W, \prec)$.
The relation is indexed by a measure $i \in W$,
written $t \sim_{e}^{i} s$.
Whenever a stuttering step occurs,
the index strictly decreases according to $\prec$.
When both programs step simultaneously,
progress is made and the measure may be freely reset.

Because the stuttering is explicitely represented,
this relation is called the \emph{explicit simulation} \parencite{cho-23-stuttering}.
The inference rules defining it are given in
\cref{fig:explicit-sim}.

\begin{figure}[htb]
  \begin{equation*}
    \begin{prooftree}
      \hypo{\isval{t} = \isval{s} = \Some{v}}
      \infer1[\textsc{ERelated}]{t \sim_{e}^{i} s}
    \end{prooftree}
    \qquad
    \begin{prooftree}
      \hypo{\step{P_s}{s}{s'}}
      \hypo{i' \prec i}
      \hypo{t \sim_{e}^{i'} s'}
      \infer3[\textsc{ESourceSteps}]{t \sim_{e}^{i} s}
    \end{prooftree}
  \end{equation*}
  \begin{equation*}
    \begin{prooftree}
      \hypo{\canp{P_t}{t}}
      \hypo{\forall t',
        \step{P_t}{t}{t'} \implies
        \exists i',
        i' \prec i \land t' \sim_{e}^{i'} s
      }
      \infer[coind]2[\textsc{ETargetSteps}]{t \sim_{e}^{i} s}
    \end{prooftree}
  \end{equation*}
  \begin{equation*}
    \begin{prooftree}
      \hypo{\canp{P_t}{t}}
      \hypo{\forall t',
        \step{P_t}{t}{t'} \implies
        \exists s',
        \exists i',
        \step{P_s}{s}{s'} \land t' \sim_{e}^{i'} s'
      }
      \infer[coind]2[\textsc{EBothSteps}]{t \sim_{e}^{i} s}
    \end{prooftree}
  \end{equation*}
  \caption{Derivation rules of the \emph{explicit simulation}.}
  \label{fig:explicit-sim}
\end{figure}

Since $(W, \prec)$ is well-founded,
an infinite sequence of stuttering steps is impossible.
This  guarantees that the explicit simulation implies behavior refinement.
